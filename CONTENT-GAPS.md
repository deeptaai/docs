# Content gaps

Per-page status for the Klaritics docs. Written 2026-09-29 during the structural cleanup on `refactor/product-guides`.

The site was built in two layers. Some pages were written against the real product; roughly half were generated by the Mintlify agent from inference and read plausibly without being accurate. This file records which is which, so nobody treats a placeholder as a source of truth.

**Rule:** do not deepen, add specifics to, or cite an unverified page. Get the product detail first, then rewrite.

## Unverified

Generated content. Every specific below is an assumption until someone confirms it.

### `deployment/self-hosted.mdx` — highest priority

The install path for a self-hosted product, in 57 lines, with no installable detail. "You will receive deployment artifacts and configuration guidance as part of your setup package" is a placeholder standing in for the entire deployment procedure.

Needed:
- Container images and registry, or the distribution mechanism
- A real `docker compose` / Helm manifest
- System requirements: CPU, RAM, disk, supported OS
- Datastore dependencies, versions, and persistence/backup guidance
- Ports, TLS termination, reverse-proxy expectations
- Where `project_id` and `server_host` actually come from after install
- Upgrade and rollback procedure

### `alerts/overview.mdx`

Claims three condition types (fixed threshold, percentage change vs. previous period, drop-to-zero/spike). Step 5 says "Use a manual test **if available**" — the writer did not know whether the feature exists.

Needed: the real condition types and operators; notification channels (email? Slack? webhook?); whether recipients are users, roles, or addresses; evaluation frequency; whether alert history exists.

### `user-management/roles.mdx`

Explicitly hedged: "These are patterns, not fixed system names." Presents Admin / Analyst / Viewer as illustrative rather than real. Also claims each user has **exactly one role**, that role changes take effect **without re-login**, and references **billing settings** — questionable for a self-hosted product.

Needed: the actual role names shipped, the real permission matrix, whether roles are custom-definable, whether multiple roles per user are allowed.

### `user-management/users.mdx`

Describes an invite → assign role → deactivate lifecycle. Needed: whether invitations are email-based, whether SSO/SAML exists, what deactivation does to a user's saved content.

### `dashboards/*.mdx` (4 pages)

`share-and-export.mdx` is the weakest: names a **Share** button "in the top right", says visibility options are "**typically** limited by role", and asserts both image export and data export exist.

Needed: real sharing model (per-user? per-role? link sharing?), which export formats actually exist, whether dashboards can be duplicated as `manage-layouts.mdx` claims.

### `widgets/*.mdx` (5 pages)

Asserts exactly four widget categories — chart, metric, table, custom — and that custom widgets can be built "from any supported analysis" with alerts configured directly on them.

Needed: confirmation the four categories are real and correctly named; what actually distinguishes a custom widget; which analyses can be pinned.

### `templates/*.mdx` (5 pages)

The four template names match `release-notes.mdx`, so the names are probably right. The widget contents attributed to each template are inferred.

Needed: the real widget list shipped in each template, and whether applying a template creates a new dashboard (as claimed) or modifies an existing one.

### `analysis/*.mdx` stubs (5 pages)

`retention.mdx`, `cohorts.mdx`, `user-flows.mdx`, `pivot-tables.mdx`, `user-sessions.mdx` — each gives a confident step-by-step build flow that was never observed. Compare any of them against `analysis/funnels.mdx` to see the depth difference.

Needed: for each, the real configuration options, metrics, and visualizations. Retention in particular claims day/week/month cohort granularity.

### `integrations/third-party-cohorts.mdx`

Describes connecting an external source, selecting cohorts, and syncing "on a schedule you define", with imported cohorts read-only. **No third-party system is ever named.**

Needed: which integrations actually exist, how auth is configured, the real sync mechanism and cadence.

## Cross-cutting

### No screenshots anywhere

Zero `<Frame>`, `<img>`, or `![]()` across all 42 pages. `images/image.png` is orphaned — nothing references it.

This costs the most on the verified deep pages, where the text describes visual output it cannot show: the Engagement Matrix quadrant chart, funnel step visualizations, the Impact Analysis Day 0 reference line, the events table, the user activity timeline.

Suggested minimum: one annotated screenshot per verified deep page, plus the dashboard and widget pages once their content is real.

### KMP missing from the v1.0.0 release notes

`sdk/kmp.mdx` is a complete 240-line guide and `sdk/overview.mdx` lists Kotlin Multiplatform among the supported SDKs, but `release-notes.mdx` says SDKs are available for "Web, Android, iOS, React Native, and Flutter" — omitting KMP.

`index.mdx` and `quickstart.mdx` were updated to include KMP during this cleanup. `release-notes.mdx` was deliberately left alone because whether KMP shipped **in v1.0.0** is a version-specific fact. Confirm and update.

### Release notes have a single entry

`release-notes.mdx` covers v1.0.0 only. Decide whether it gets maintained per release and what the entry format should be.

### No API or data-model reference

The site documents the UI and the client SDKs. There is no reference for an ingestion API, query API, export API, or the event/property data model. Confirm whether these are public surfaces that need documenting.
